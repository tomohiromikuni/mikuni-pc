## 1. 要件整理（STEP 1）

### 1-1. 利用者と、できること

| 区分 | できること |
|---|---|
| **管理者** | すべての機能。スタッフの追加・権限設定、全訓練生の管理 |
| **スタッフ・講師** | 許可された範囲（担当コース・クラス、許可された機能）だけの閲覧・配信・返信 |
| **訓練生** | 自分あてのお知らせを読む、アンケート・出欠に回答する、事務局とのチャット |

### 1-2. 機能の一覧（依頼書から整理）

| 機能 | 主な内容 |
|---|---|
| 招待・ログイン | 招待URL／QRコード、ログイン、利用停止・再開 |
| 訓練生管理 | 手動登録、Excel・CSV一括登録（取り込み前の確認・エラーチェック）、検索・絞り込み、出欠・回答履歴 |
| コース・クラス管理 | 登録・編集・削除、所属設定・所属変更 |
| お知らせ | 全体／コース／クラスへの配信、画像・PDF添付、優先度、予約配信、カテゴリー、既読・未読確認、配信履歴 |
| チャット | 訓練生⇔事務局の1対1、テキスト・画像・ファイル、履歴、新着通知 |
| アンケート・出欠 | 選択式・自由記述、出席／欠席／遅刻、期限、対象指定、未回答者一覧、集計・グラフ |
| プッシュ通知 | お知らせ・チャット・アンケート依頼。平日20時〜翌7時・土日・祝日は訓練生に通知しない |
| スタッフ管理 | 担当範囲と機能ごとの権限 |

### 1-3. 不足している要件・注意点（指摘事項）

依頼書はよくまとまっていますが、作る前に決めておかないと、あとで作り直しになりやすい点があります。

**① 出欠確認の位置づけ**
- 「訓練生が自分で回答する出欠確認（例：明日来られますか？）」と、「講師が付ける正式な出席簿」は別物です。
- 職業訓練では、行政（ハローワーク等）に出す正式な出席簿がある場合が多いです。このアプリの出欠を**正式記録として使うか、連絡用の参考情報にとどめるか**を決めたいです。
- 正式記録にするなら、訂正の履歴を残す・早退を入れるなど、要件が増えます。
- **決定：** 「連絡用の出欠回答」として作ります。正式な出席簿は将来の追加機能にします。

**② チャットの相手は「事務局窓口」か「個々のスタッフ」か**
- **推奨：** 訓練生からは「事務局」という1つの相手に見えるようにします。中では権限を持つスタッフ全員が見て返信できる、共有の受付窓口の形です。担当者が休んでも対応が止まりません。
- 訓練生どうしのチャットは、トラブル防止と個人情報保護のため**作らない**ことを推奨します。

**③ 祝日以外のお休み**
- 年末年始（12/29〜1/3など）や訓練校独自の休講日は、「国民の祝日」には含まれません。
- 管理者が**休校日を自分で追加できる**画面を用意します。

**④ 修了後のデータの扱い**
- **決定（確認中）：** 修了予定日の**90日後にアカウントを自動停止**します。
- 停止後に個人情報・チャット履歴をいつ削除するかは確認中です（9章の質問3）。
- 個人情報保護の観点から、**保管期間と削除のルール**は必ず決めておくべき項目です。

**⑤ プライバシーポリシーと同意**
- 個人情報を扱うため、初回ログイン時に「利用規約・プライバシーポリシーへの同意」画面を出すことを推奨します。
- 文面は運営側でご用意いただく必要があります（ひな形は作れます）。

**⑥ ログインできなくなったときの対応**
- パスワード忘れや機種変更への対応が必要です。
- **推奨：** メールでパスワードを再設定できるようにします。メールが使えない訓練生には、管理者が招待をやり直せるようにします。
- メールアドレスを持っていない訓練生がいるかどうかも確認したいです。

**⑦ iPhoneの通知には条件がある**
- iPhoneでWebアプリの通知を受け取るには、次の条件をすべて満たす必要があります。
  - iOS 16.4以上であること
  - Safariで「ホーム画面に追加」したアプリから開くこと
  - 本人が通知を許可するボタンを押すこと
- 通知の許可を求める方法と、訓練生向けの設定ガイドを作ります（詳しくは5章）。

**⑧ お知らせ送信後の修正・取り消し**
- 送信したお知らせを修正・削除できるようにするかどうか。
- **推奨：** 修正可能とし、画面に「編集済み」と表示します。削除は管理者のみ可能にします。

**⑨ アンケートの匿名・記名**
- 依頼書に「誰が未回答か分かる」とあるため、基本は記名式です。
- 授業評価など、匿名にしたいアンケートがあるかを確認したいです。

**⑩ 添付ファイルの上限**
- 1ファイル10MBまで、画像は送信時に自動で縮小、を推奨します。
- 保存容量と費用を抑えるためです。

**⑪ コース・クラスの「削除」**
- 訓練生や履歴が結びついているコースを完全に消すと、過去の記録が壊れます。
- **推奨：** 削除ではなく「アーカイブ（終了扱いにして非表示）」にします。

**⑫ 将来、複数の訓練校で使う可能性**
- 可能性が少しでもあるなら、最初から「組織（学校）」という単位をデータに入れておくと、あとで楽になります。
- 余分な手間はわずかなので、**最初から入れておくことを推奨**します。

## 2. 技術構成の提案（STEP 2）

### 2-1. 3つの選択肢の比較

| | **A案：Supabase + Next.js（推奨）** | B案：Firebase | C案：レンタルサーバー（VPS）に自前構築 |
|---|---|---|---|
| どんなもの | データベース・ログイン・ファイル保存・リアルタイム通信がセットになったサービス | Googleの同種サービス | サーバーを1台借りて全部自分で作る |
| データの形 | 表形式（Excelのような表）。集計・絞り込みが得意 | 書類の束のような形。集計や複雑な絞り込みは苦手 | 自由 |
| 個人情報の守り | **行単位のアクセス制御**をデータベースが強制。「他人のデータが見えない」をシステムの根元で保証できる | ルールで制御可能。ただし書き方が複雑になりやすい | 全部自前。設定ミスのリスクが最も高い |
| 日本にデータを置く | 東京リージョンを選べる | 東京リージョンを選べる | 国内業者を選べる |
| バックアップ | 有料プランで毎日自動 | 自分で設定が必要 | 自分で設定が必要 |
| 月額 | 約4,000〜7,000円 | 小規模なら0〜数千円（従量課金で読めない） | 約1,000〜3,000円 |
| 保守の手間 | 少ない（サーバー管理不要） | 少ない | **多い**（OS更新・セキュリティ対策を自分で） |
| 向いている点 | 管理画面の集計・権限管理が多い、今回のようなアプリ | チャット中心のアプリ | 技術者が常駐している組織 |

### 2-2. 推奨：A案

**理由（重視事項との対応）**
1. **個人情報の保護（重視事項4）**
   - 「訓練生は自分の行だけ」「スタッフは担当クラスの行だけ」というルールを、データベース自体に設定できます（行単位セキュリティ＝RLS）。
   - 画面側にバグがあっても、データベースが他人の情報を渡さない二重の守りになります。
2. **集計・検索が得意（重視事項3）**
   - 表形式のデータベース（PostgreSQL）なので、アンケート集計・出欠履歴・絞り込みに向いています。
3. **維持費と手間のバランス（重視事項5）**
   - サーバー管理が不要で、毎日の自動バックアップ込みで月数千円です。
4. **将来の拡張（重視事項6）**
   - PostgreSQLは世界標準のデータベースです。将来ほかのサービスに引っ越すこともできます。

### 2-3. 具体的な構成

```
 [スマホ・PC のブラウザ / ホーム画面のアプリ(PWA)]
                 │
                 ▼
   ┌───────────────────────────┐
   │  Webアプリ本体（Next.js）       │  ← Vercel に設置
   │  訓練生画面 / 管理画面            │
   └───────────────────────────┘
                 │
                 ▼
   ┌───────────────────────────┐
   │  Supabase（東京リージョン）       │
   │  ・データベース(PostgreSQL+RLS)   │
   │  ・ログイン認証                   │
   │  ・ファイル保存(画像・PDF)         │
   │  ・リアルタイム(チャット即時表示)   │
   │  ・定期実行(予約配信・通知処理)     │
   └───────────────────────────┘
                 │
     ┌───────────┴───────────┐
     ▼                       ▼
 Web Push(通知・無料)     メール送信(招待・再設定)
                          Resend 等(月3,000通まで無料)
```

| 役割 | 使うもの | ひとこと説明 |
|---|---|---|
| 画面・アプリ本体 | **Next.js（React）＋TypeScript** | 最も利用者の多いWeb開発の仕組み。情報や技術者が見つけやすい |
| 見た目 | Tailwind CSS | スマホ・PC両対応の画面を作りやすい |
| 設置場所 | **Vercel** | Next.jsの開発元のサービス。更新が簡単 |
| データベース・認証・ファイル | **Supabase（Proプラン・東京）** | 上記のとおり |
| 通知 | **Web Push（VAPID方式）** | ブラウザ標準の通知。追加費用なし |
| メール | Resend など | 招待メール・パスワード再設定用 |
| 祝日 | 内閣府「国民の祝日」CSV | 年1回自動で取り込み＋管理画面で休校日を追加 |
| Excel/CSV読み込み | SheetJS（ブラウザ内で処理） | 取り込み前に画面で確認できる |
| グラフ | Recharts | アンケート集計のグラフ |

### 2-4. ログイン方式の提案

| 対象 | 方式 |
|---|---|
| 訓練生 | 招待URL／QRコードを開く → 自分でパスワードを決める → 以後は**メールアドレス＋パスワード**でログイン。ログイン状態はスマホに保持し、毎回入力しなくてよいようにします |
| スタッフ・管理者 | メール＋パスワード＋**2段階認証（認証アプリ）**を必須にします。個人情報をまとめて見られる立場のためです |

- 招待URLは**1人1回限り・有効期限7日**とし、使い回しを防ぎます。
- 期限切れの場合は、管理者が招待を再発行できます。
- ほかの方式との比較:
  - メールに届くリンクだけでログインする方式：パスワードは不要ですが、メールを見慣れない人には難しくなります。
  - SMS認証：送信のたびに費用がかかります。
  - LINEログイン：将来の選択肢として残せます。

## 3. 画面設計（STEP 3）

### 3-1. 訓練生側（スマホ優先・下にタブ5つ）

```
┌────────────────────────┐
│  ○○職業訓練校       🔔    │
├────────────────────────┤
│ ⚠ 重要：明日は休講です      │ ← 重要・緊急は最上部に赤帯
│                          │
│ 📝 回答が必要なもの (2)     │ ← 未回答の出欠・アンケート
│   ・明日の出欠  期限 今日18時 │
│   ・授業アンケート 期限 金曜  │
│                          │
│ 📢 新着のお知らせ           │
│   ・●11/18 健康診断の案内    │ ← ●=未読
│   ・ 11/17 教室変更について   │
├────────────────────────┤
│ 🏠    📢    💬    📝    👤  │
│ホーム お知らせ チャット 回答 マイページ│
└────────────────────────┘
```

| # | 画面 | 内容 |
|---|---|---|
| S-1 | 招待からの初回登録 | 招待URL／QRから開く → 本人確認（氏名表示） → パスワード設定 → 規約同意 |
| S-2 | ログイン | メール＋パスワード、パスワードを忘れた方 |
| S-3 | ホーム | 重要なお知らせ、回答が必要なもの、新着のお知らせ、未読チャット数 |
| S-4 | お知らせ一覧 | カテゴリーで絞り込み、未読マーク、過去分も閲覧 |
| S-5 | お知らせ詳細 | 本文・画像・PDF。開いた時点で既読 |
| S-6 | チャット（事務局） | LINE風の吹き出し、写真・ファイル送信 |
| S-7 | 回答一覧 | 未回答／回答済みのタブ |
| S-8 | 出欠・アンケート回答 | 大きな選択ボタン（出席／欠席／遅刻）、期限内なら回答を修正可能 |

**分かりやすさの工夫**
- 文字は基本16px以上、ボタンは指で押しやすい大きさ（高さ44px以上）にします。
- アイコンには必ず文字ラベルを付けます。
- 1画面で1つのことだけを行う設計にします。
- 色だけに頼らず「重要」「緊急」と文字でも表示します。
- 時刻は「今日 18:00」のように分かりやすく表示します。

### 3-3. 主な画面の流れ

**訓練生が使い始めるまで**
```
管理者: 一括登録(A-5) → 招待発行(A-6) → QRを印刷して配布 / メール送信
訓練生: QRを読み取る → 初回登録(S-1) → ホーム画面に追加(S-10) → 通知を許可 → ホーム(S-3)
```

**お知らせ**
```
スタッフ: お知らせ作成(A-9) → プレビュー → 送信 or 予約
訓練生:   通知 → タップ → お知らせ詳細(S-5)  ※自動で既読
スタッフ: 既読状況(A-10) → 未読者に再通知
```

**出欠確認**
```
スタッフ: 出欠を作成(A-13)「11/19の出欠」宛先=Aクラス 期限=18時
訓練生:   ホームの「回答が必要なもの」 → 出席/欠席/遅刻を選ぶ(S-8)
スタッフ: 集計(A-14)で未回答者を確認 → リマインド
```

## 4. データ設計

データベースに作る「表」の一覧です。※印の項目は個人情報で、行単位のアクセス制御の対象です。

### 4-1. 利用者・組織

| 表 | 主な項目 |
|---|---|
| organizations（組織） | 名前 ※将来の複数校対応用 |
| profiles（利用者） | 役割（管理者/スタッフ/訓練生）、※氏名、※フリガナ、※メール、※電話、利用状態（有効/停止）、規約同意日時 |
| trainee_details（訓練生情報） | 利用者、入校日、修了予定日 |
| invitations（招待） | 利用者、招待コード（推測できない文字列）、有効期限、使用日時 |
| staff_scopes（スタッフ担当範囲） | スタッフ、担当コース・クラス（または全体） |
| staff_permissions（スタッフ権限） | スタッフ、権限の種類（個人情報閲覧／チャット閲覧・返信／お知らせ配信／アンケート作成／訓練生編集） |

### 4-2. コース・クラス

| 表 | 主な項目 |
|---|---|
| courses（コース） | 名前、開始日、終了日、アーカイブ済みか |
| classes（クラス） | コース、名前、アーカイブ済みか |
| enrollments（所属） | 訓練生、クラス、所属開始日、所属終了日 ※所属変更の履歴が残る |

### 4-3. お知らせ

| 表 | 主な項目 |

## 5. 通知の仕組みと「通知しない時間帯」

### 5-1. 対応端末

| 端末 | 対応 | 条件 |
|---|---|---|
| Android（Chrome） | ◎ | 通知を許可するだけ |
| PC（Chrome / Edge / Safari / Firefox） | ◎ | 通知を許可するだけ。ブラウザが起動している必要あり |
| iPhone / iPad | ○ | iOS 16.4以上、Safariで「ホーム画面に追加」して、そのアイコンから開き、通知を許可する |

- iPhoneの条件を満たしていない利用者には、ホーム画面で「通知を受け取るにはホーム画面に追加してください」と案内を出します。
- 管理画面では「通知が届く設定になっている訓練生」の割合を確認できるようにします。
- **通知はあくまで「お知らせを見に来てもらうきっかけ」です。** 通知が届かない人でも、アプリを開けば赤い未読マークで分かるようにします。

### 5-2. 通知しない時間帯のルール（訓練生のみ）

送信しようとした時点が次のいずれかなら、通知を**保留**します。
- 毎日 20:00〜翌7:00
- 土曜日・日曜日
- 国民の祝日
- 管理者が登録した休校日

お知らせやメッセージ自体はすぐにアプリ内に保存され、アプリを開けばいつでも見られます。保留するのは**スマホに鳴る通知だけ**です。

スタッフ・管理者への通知（訓練生からのチャット着信など）は時間制限なしとし、個人ごとにオン／オフできるようにします。

### 5-3. 保留した通知の扱い（提案）

**推奨：次の「通知してよい時間」の最初（平日の朝7:00）に、まとめて1通だけ送る**

> 例：「お知らせ3件、メッセージ2件が届いています」

- 金曜の夜に5件届いても、月曜の朝に1通だけ届くので、通知が大量に鳴りません。
- 月曜が祝日なら火曜の7:00になります。

**管理者向けの「緊急通知」（提案・初期設定はオフ）**
- 優先度「緊急」のお知らせに限り、管理者が確認ダイアログで「時間外でも今すぐ通知する」を選べる機能です。
- 災害による休講連絡などを想定しています。
- 使うかどうかは運営方針で決めてください。

### 5-4. 祝日データ

- 内閣府が公開している「国民の祝日」CSVを、年1回自動で取り込みます。
- 取り込みに失敗した場合に備えて、管理画面から手動で追加・修正もできるようにします。
- 祝日が法改正で変わっても、データを入れ替えるだけで対応できます。

### 5-5. 仕組み（技術メモ）

```
お知らせ配信/チャット送信
   → notification_queue に「送信予定」として登録
   → 定期処理（数分おき）が予定日時を過ぎたものを確認
       → 通知禁止時間か？ → はい：次の通知可能時刻に予定を変更（まとめ通知に合流）
                          → いいえ：Web Push で送信
```

予約配信も同じ定期処理で行います。

## 6. セキュリティ・個人情報の守り方

| 対策 | 内容 |
|---|---|
| 招待制 | 一般の新規登録ボタンは作りません。招待コードは推測不能・1回限り・期限つきです |
| 行単位のアクセス制御 | 訓練生は自分のデータのみ。スタッフは担当範囲かつ許可された権限のみ。**データベース側で強制**します |
| 個別チャットの保護 | チャット閲覧権限を持つスタッフと本人以外は、データベースから取り出せません |
| 管理者・スタッフの2段階認証 | パスワードが漏れても不正ログインされにくくします |
| 通信の暗号化 | すべてHTTPS |
| 保存データの暗号化 | Supabase側で保存時に暗号化されます |
| ファイルの限定公開 | 数分だけ有効なURLで配信します |
| 操作ログ | 個人情報の閲覧・CSV出力・権限変更を記録します |
| 利用停止 | 停止した瞬間にログイン不可になり、ログイン中の端末も追い出します |
| バックアップ | 毎日自動（7日分）。重要な時期は手動で追加取得し、月1回は復元手順を確認します |
| データの保管場所 | 日本（東京リージョン） |

テスト段階では、**「訓練生Aでログインして、訓練生Bのデータを取りに行く」といった攻撃役のテストを自動化**して、他人の情報が見えないことを確認します。

## 7. 開発の進め方（STEP 4〜6）

一度に全部は作らず、**動くものを段階的に確認していただきながら**進めます。各段階の終わりに、実際の画面を触って確認していただきます。

| 段階 | 内容 | 終わったときにできること |
|---|---|---|
| **0. 準備** | 開発環境、Supabase・Vercelの契約（最初は無料枠）、データベースの土台、権限ルール | 空のアプリが公開URLで開ける |
| **1. 基本機能（最小構成）** | ログイン・招待、コース・クラス管理、訓練生の手動登録、お知らせ（テキスト・宛先指定・既読管理）、訓練生ホーム | 管理者がお知らせを出し、訓練生が読み、既読が確認できる |
| **2. 添付と一括登録** | 画像・PDF添付、カテゴリー・優先度、Excel/CSV一括登録（確認画面つき）、QR一括発行 | 実際のクラス全員を登録して配信できる |
| **3. チャット** | 事務局チャット、写真・ファイル送信、受信箱、対応状態 | 個別相談をアプリで受けられる |
| **4. 出欠・アンケート** | 作成・回答・未回答者一覧・集計グラフ・CSV出力 | 出欠確認とアンケートをアプリで完結 |
| **5. 通知とPWA** | ホーム画面追加、Web Push、通知禁止時間、まとめ通知、祝日・休校日、予約配信 | スマホに通知が届く |
| **6. 権限の細分化と運用機能** | スタッフ権限の細かい設定、2段階認証、操作ログ、訓練生の履歴画面、修了後の自動停止 | 複数スタッフで安全に運用できる |
| **7. テスト** | 依頼書STEP 5の7項目＋権限の攻撃テスト、iPhone/Android/PCでの実機確認 | 確認結果の一覧表 |
| **8. 試験運用 → 本番** | 1クラスで試験運用 → 改善 → 全体に展開、運用マニュアル（管理者向け・訓練生向け） | 本番運用開始 |

**テストの考え方（STEP 5）**
- 権限まわり（他人の情報・チャットが見えないこと）は、**自動テスト**で毎回確認します。
- 通知時間の制限は、「金曜21時」「祝日」「年末年始」などの日時を**疑似的に作って**正しく判定されるか自動テストします。
- 集計は、決まった回答データを入れて、正しい数字になるか確認します。
- スマホの見た目は、実機（iPhone・Android）とPCで確認します。

**公開・運用（STEP 6）で用意するもの**
- 公開URL（独自ドメイン推奨）
- 管理者向けマニュアル（登録・配信・集計の手順）
- 訓練生向けの1枚ものの案内（QRコード＋ホーム画面追加の手順）
- バックアップと復元の手順書
- 毎月の費用と、利用者が増えたときの目安
